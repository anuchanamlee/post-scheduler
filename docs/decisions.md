# สิ่งที่ตัดสินไว้ และสิ่งที่ยังไม่ได้พิสูจน์

รายงานวิเคราะห์สเปกฉบับเต็มอยู่ที่ `Downloads/New folder/analysis-report.md`

## ตัดสินไปแล้ว 3 ข้อ

### A1 · ท่าเชื่อมต่อ Meta → ใช้ท่าที่เอกสารรองรับ
ให้ลูกค้า (บัญชี Facebook คนจริง) ถือ role บนแอป แล้วใช้ System User token ยิง API
**เหตุผล**: ท่าเดิม (System User อย่างเดียว) ไม่มีเอกสาร Meta รองรับ ท่านี้มีข้อความรองรับตรงๆ
**ผลต่อโค้ด**: ไม่มีเลย — ต่างกันแค่ runbook ตอน onboard
**ยังต้องทำ**: ทดสอบกับแอปจริง 1 อัน ถ้าท่าเดิมใช้ได้ ก็ตัดขั้นที่ 3 ของ runbook ทิ้งได้

### B1 · ขอบเขต tenant → deploy แยก + schema multi-tenant
1 instance ต่อ 1 ลูกค้า (DB แยก) แต่ทุกตารางมี `tenant_id` ตั้งแต่วันแรก
**เหตุผล**: ได้ความง่ายของวันนี้ โดยไม่ปิดทางของวันหน้า ราคา = 1 column + helper 1 ตัว
**วันที่รวม DB**: เปิด RLS ไม่ต้อง migrate ข้อมูล

### B7 · โปสเตอร์สินค้า → เทมเพลต + รูปสินค้าจริง (ไม่ใช้ AI วาดภาพ)
**ตัดสินเมื่อ 4 ก.ย. 2026 หลังลูกค้าถามถึงส่วนสร้างโปสเตอร์**

เหตุผลที่ไม่ให้ AI สร้างภาพสินค้า: โปสเตอร์ขายของต้องเป็นสินค้าของร้านนั้นจริงๆ
AI วาดกาแฟสวยได้แต่ไม่ใช่กาแฟของร้านนี้ — ลูกค้าปลายทางเห็นของจริงแล้วไม่ตรง
= เสียความน่าเชื่อถือมากกว่าที่ได้ และเอกสารข้อเสนอเองก็เขียนไว้แล้วว่า
"AI เขียนตัวอักษรไทยไม่ได้ ต้องวางข้อความทับด้วยฟอนต์จริง"

**สิ่งที่ทำแทน**: เทมเพลต 6 แบบ (ลดราคา · ของใหม่ · เมนูแนะนำ · เวลาเปิด-ปิด ·
ซื้อ 1 แถม 1 · ประกาศทั่วไป) × 3 สัดส่วน — ร้านถ่ายสินค้าเอง ระบบจัดวางกับข้อความให้
ตัวหนังสือใช้ฟอนต์ไทยจริง (Garuda/Loma) คมชัด 100% ผลลัพธ์เหมือนเดิมทุกครั้ง
ไม่มีค่าใช้จ่ายต่อภาพ

**ปรับแล้ว 6 ก.ย. 2026 — เพิ่มการสร้างภาพด้วย AI (เจ้าของสั่ง)**

ข้อสรุปข้างบนไม่ได้ถูกกลับ แต่ถูกกันขอบเขต: AI สร้าง**ฉาก**ได้ ไม่ได้สร้าง**สินค้า**

| ทำได้ | ยังไม่ทำ และตั้งใจไม่ทำ |
|---|---|
| ฉากพื้นหลังไว้วางข้อความทับ | ให้ AI วาดสินค้าของร้านขึ้นมาใหม่ |
| ภาพประกอบโพสต์ที่ไม่มีตัวสินค้า | ให้ AI เขียนตัวอักษรไทยลงในภาพ |
| เปลี่ยนพื้นหลังของ**รูปสินค้าจริง** (image-to-image) | |
| จัดองค์ประกอบโปสเตอร์ทั้งใบ แล้วเราวางข้อความทับ | |

สองข้อจำกัดถูกบังคับด้วยโค้ด ไม่ใช่ด้วยคำเตือนในเอกสาร:
- prompt ทุกโหมดมีท่อน `NO_TEXT` (`src/content/image.ts`) และมีเทสต์ยืนยันว่ามีอยู่ทุกโหมด
  ข้อความไทยยังวาดด้วย Garuda/Loma ใน `poster.ts` เหมือนเดิมทุกกรณี
- โหมด replace-bg บังคับต้องมีรูปต้นฉบับ และปฏิเสธ id ที่ไม่ใช่ของ tenant นั้น

**ผลต่อเอกสารข้อเสนอ**: ตารางเปรียบเทียบที่เขียนว่า "AI สร้างภาพโปสเตอร์ ✓" ตอนนี้
ใกล้ความจริงแล้วแต่ยัง**ห้ามใช้ตามนั้นตรงๆ** — ต้องเขียนให้ตรงว่า
"AI สร้างฉาก/พื้นหลัง + เปลี่ยนพื้นหลังรูปสินค้าจริง · ข้อความไทยวางด้วยฟอนต์จริง"
ถ้าลูกค้าเข้าใจว่า AI วาดสินค้าให้ได้เลย จะผิดหวังตอนใช้จริง

**ผลต่อราคา**: ภาพมีต้นทุนต่อใบ (~$0.04) ต่างจากโปสเตอร์เทมเพลตที่ฟรี
เพดานตั้งไว้ 60 ใบ/เดือน/ลูกค้า = ~$2.4 ยังอยู่ใต้เพดานรวม $5
ถ้าจะขายเป็นจุดขาย ต้องคิดค่านี้เข้าไปในค่าดูแลรายเดือนก่อน

## ยังไม่ได้ยืนยัน — อย่าเชื่อจนกว่าจะเช็ค

| เรื่อง | สถานะ | ทำอะไรก่อนใช้จริง |
|---|---|---|
| System User = role user ใน Dev Mode | ไม่มีในเอกสาร Meta | **มีสคริปต์แล้ว**: `npm run verify-meta -- --token ...` |
| BOBO ต้อง verify ธุรกิจก่อนไหม | เอกสารเงียบ ไม่ยืนยันทั้งสองทาง | ลองเรียก `managed_businesses` จริง |
| ชื่อ scope `instagram_business_content_publish` | ยังไม่ยืนยันกับ permission reference | `verify-meta` อ่าน scope จริงจาก `debug_token` ให้ |
| HTTPS บังคับสำหรับ `image_url` ไหม | เอกสารบอกแค่ "publicly accessible" | ใช้ HTTPS ไปเลย ไม่ต้องเสี่ยง |
| VIDEO → REELS deprecated | ยังไม่ยืนยัน | เช็คก่อนถ้าจะรองรับวิดีโอ |
| คุณภาพจริงของ gemini-2.5-flash-image กับฉากไทย | **ยังไม่เคยยิงจริงสักครั้ง** — ยังไม่มี OPENROUTER_API_KEY | ตั้ง key แล้วสร้าง 5-10 ใบ ดูว่าฉากออกมาใช้ได้ไหม และมันแอบใส่ตัวอักษรมาจริงไหมทั้งที่สั่งห้าม |
| ราคาต่อใบจริงที่ OpenRouter คิด | อ้างจากเอกสาร ยังไม่เห็นบิลจริง | ดู `usage.cost` ที่บันทึกลง `ai_usage` หลังยิงจริงรอบแรก |
| โหมด replace-bg รักษาตัวสินค้าได้จริงแค่ไหน | ท่านี้พึ่งความสามารถของโมเดล ไม่ใช่ของเรา | ทดสอบกับรูปสินค้าจริงของลูกค้าก่อนโฆษณาว่าทำได้ |

## ยืนยันแล้วจากเอกสาร Meta (4 ก.ย. 2026 · v26.0)

- Development Mode + role user = ไม่ต้อง App Review และไม่ต้อง Business Verification
- System User token ตั้งไม่หมดอายุได้จริง แต่**เงื่อนไขที่ทำให้พัง Meta ไม่ได้เขียนไว้**
  → safety net (จับ error 190) ห้ามตัดออก
- **IG rate limit = 100 โพสต์/24 ชม.** ไม่ใช่ 25 (เลข 25 คือของปี 2018)
- IG container ไม่ publish ใน 24 ชม. → `EXPIRED` · Meta แนะนำ poll นาทีละครั้ง ≤ 5 นาที
  (ค่าใน `src/lib/env.ts` ตั้งตามนี้)

## ทำเสร็จแล้วหลังรายงานฉบับแรก

- **เก็บสถิติผลตอบรับ** (`/insights`) — ฐานของแพ็กเกจ 3
  - เก็บ 3 ช่วง: **1 ชม. · 24 ชม. · 7 วัน** หลังโพสต์ขึ้นจริง ไม่ใช่ตัวเลขล่าสุดตัวเดียว
    (รายงานข้อ C7) — ยอด 1 ชม. บอกว่า "เวลานี้คนเห็นไหม" ยอด 24 ชม. บอกว่า "คอนเทนต์นี้ดีไหม"
    ถ้าเก็บทับกันจะแยกสองเรื่องนี้ไม่ออก และเทียบข้ามโพสต์ไม่ได้เพราะสะสมยอดมาไม่เท่ากัน
  - `fetchMetrics` เป็น method ที่**ไม่บังคับ**ใน provider — ปลายทางที่ไม่มีข้อมูลก็ไม่ต้องมี
  - FB นับจาก `likes.summary` + `insights` · IG ต้องเรียก `/insights` แยก และ `saved` มีเฉพาะ IG
  - **ช่วงเวลาที่ได้ผลดีที่สุด** คำนวณจากยอด 24 ชม. แสดงเฉพาะช่วงที่มี ≥2 โพสต์
    และบอกจำนวนที่ใช้คำนวณทุกแถว — ตัวเลขจากโพสต์เดียวไม่ใช่ข้อสรุป
  - ดึงสถิติไม่ได้ไม่ทำให้รอบ worker พัง (โพสต์อาจถูกลบ หรือ token หมดสิทธิ์อ่าน insights)
- **เลือกกรอบครอปเอง** (`/crop/<id>`)
  - เดิม `position: attention` ให้ sharp เดาจุดสำคัญ — เดาถูกบ้างผิดบ้าง ตัดหัวคนในรูปหมู่
    ตัดสินค้าออกเหลือแต่พื้นหลัง แล้วเจ้าของร้านมารู้ตอนโพสต์ขึ้นแล้ว
  - คลิกจุดที่ต้องให้อยู่ในกรอบ · กรอบสีเลื่อนตาม · พรีวิวสดข้างๆ
  - **พรีวิวใช้ CSS `object-position` เป็นเปอร์เซ็นต์ ตรงกับที่เซิร์ฟเวอร์คำนวณ** — ที่เห็นคือที่ได้
  - เขียน `cropRect` เองแทน gravity ของ sharp เพราะ gravity เลือกได้แค่ 9 จุดตายตัว
  - เก็บจุดที่เลือกไว้ กลับมาแก้ได้ · ครอปกี่รอบก็ได้ ต้นฉบับไม่ถูกแตะ
- **ลากเลื่อนโพสต์ในปฏิทินเดือน**
  - เดิมเลื่อนเวลาต้อง เข้าหน้าแก้ → เลือกเวลา → บันทึก (3 ขั้น) ตอนนี้ลากทีเดียว
  - **เวลาในวันคงเดิม** เพราะคนที่ลากตั้งใจเลื่อน "วัน" ไม่ใช่เปลี่ยนเวลาที่คิดมาแล้ว
  - คำนวณวันใหม่ด้วย SQL (`$3::date + time AT TIME ZONE`) ไม่ใช่ Date ของ JS —
    การประกอบ "วันนั้นเวลาเดิมตามเวลาไทย" บนเซิร์ฟเวอร์ UTC เป็นบ่อเกิดบั๊กเวลาที่หายาก
  - ของที่ขึ้นเพจแล้วลากไม่ได้ (`draggable=false`) เพราะเลื่อนไม่ได้อยู่แล้วในความจริง
  - ย้ายมาไว้อดีต = ระบบบอกว่าเลยเวลาแล้ว ไม่ปล่อยให้กลายเป็น missed เงียบๆ
  - ช่องปฏิทินแสดงโพสต์จริง (เวลา + แคปชั่นย่อ + แถบสีสถานะ) ไม่ใช่แค่ตัวเลข
- **ล้าง log เก่าอัตโนมัติ (retention)**
  - `job_runs` เขียน 1 แถวทุก 15 วิ = 5,760 แถว/วัน = ~2.1 ล้าน/ปี ถ้าไม่ล้าง
  - เก็บ: heartbeat 7 วัน · log API 30 วัน · แจ้งเตือนที่อ่านแล้ว 90 วัน · ร่างที่ไม่ได้ใช้ 90 วัน
  - **แจ้งเตือนที่ยังไม่อ่านไม่ถูกลบ ไม่ว่าเก่าแค่ไหน** · โพสต์/รูป/โปสเตอร์/credential ไม่เคยถูกแตะ
  - ลบทีละก้อน 5,000 แถว ไม่ใช่ DELETE ทีเดียวล้านแถว — การลบก้อนใหญ่ล็อกตารางนาน
    แล้ว worker รอบนั้นค้าง ซึ่งแปลว่าโพสต์ที่ถึงเวลาไม่ถูกส่ง
  - รันวันละครั้งหลังส่งโพสต์เสร็จ — งานบ้านต้องไม่มาก่อนงานที่ลูกค้าจ่ายเงินให้ทำ
  - `/api/health` รายงานขนาดตารางที่โตเร็ว และเตือนถ้า `job_runs` ใหญ่ผิดปกติ
- **คลังรูป + ดาวน์โหลดไฟล์** (ของที่สัญญาไว้ในแพ็กเกจ 1)
  - `/library` รวมโปสเตอร์กับรูปที่อัปโหลด กรองแยกได้ บอกว่าใช้ในโพสต์ไหนบ้าง
  - ครอปสัดส่วนใหม่จากคลังได้เลย ต้นฉบับไม่ถูกแตะ
  - **ลบรูปที่ยังมีโพสต์รอส่งใช้อยู่ไม่ได้** ไม่งั้นถึงเวลาโพสต์แล้วรูปหาย
  - ลบแล้วไฟล์จริงหายจากที่เก็บด้วย ไม่ใช่แค่ซ่อนแถว (ค่าเก็บของยังเดินอยู่)
  - `?download=1` ส่ง `Content-Disposition: attachment` ให้เบราว์เซอร์บันทึกไฟล์
- **ขั้นตอนอนุมัติ + สิทธิ์ผู้ใช้ 3 ระดับ** (ของที่สัญญาไว้ในแพ็กเกจ 2)
  - `owner` ทำได้ทุกอย่าง · `approver` เขียน+อนุมัติ · `editor` เขียนอย่างเดียว
  - เปิด/ปิดขั้นตอนอนุมัติได้ต่อลูกค้า — ร้านที่เจ้าของทำเองคนเดียวไม่ต้องเสียเวลา
  - **บังคับสิทธิ์ที่ชั้น action ไม่ใช่แค่ซ่อนปุ่ม** (`requireRole`) เพราะซ่อนปุ่มกันคนที่ไม่ตั้งใจ
    ไม่ได้กันคนที่ตั้งใจ
  - ตีกลับต้องบอกเหตุผลเสมอ และคนเขียนได้รับแจ้งเตือน — ไม่บอกก็แก้ไม่ถูกแล้วส่งกลับมาแบบเดิม
  - บันทึกว่าใครอนุมัติเมื่อไหร่ ถ้าโพสต์มีปัญหาทีหลังจะรู้ว่าใครปล่อยผ่าน
  - ต้องเหลือเจ้าของอย่างน้อย 1 คนเสมอ · เปลี่ยนสิทธิ์ตัวเองไม่ได้
- **ที่เก็บไฟล์ถอดเปลี่ยนได้ (local / S3-compatible)**
  - เดิมรูปอยู่ใน volume ของ container — VPS ตายทีเดียวหายหมด และรูปคือของที่ลูกค้าทำเอง
  - `STORAGE_DRIVER=s3` ใช้ได้กับ Cloudflare R2 / Backblaze B2 / MinIO / S3 จริง
  - ลงลายมือชื่อ SigV4 เองแทนการลาก `@aws-sdk/client-s3` (~10 MB) เข้ามาเพื่อ 3 คำสั่ง
  - route `/media/...` redirect ไปต้นทางเมื่อใช้ S3 — ไฟล์ไม่ต้องวิ่งผ่าน event loop ของเว็บ
  - ทดสอบกับ MinIO ใน compose (`--profile s3`) ไม่ต้องมีบัญชีคลาวด์
- **โควตา Instagram 100 โพสต์/24 ชม. กันเองก่อนยิง**
  - เดิมปล่อยให้ Meta ปฏิเสธ ซึ่งระบบตีเป็น rate limit แล้ว retry ทุก 15 นาที
    ถ้าคิวมี 30 โพสต์ ทั้ง 30 ตัวจะวนยิงพร้อมกัน เผาโควตา API ที่เหลือ
    และ attempt_count หมดจนโพสต์ตายทั้งชุดทั้งที่ไม่มีอะไรผิด
  - ตอนนี้เช็คก่อนยิง เต็มแล้วเลื่อนไปรอจนช่องว่าง **ไม่นับเป็นครั้งที่ลองแล้วล้ม**
  - Facebook ไม่ถูกกระทบ · แถบในหน้าคิวเปลี่ยนสีตามระดับ · เตือนล่วงหน้าตอนเหลือ ≤10%
  - `/api/health` รายงานโควตาด้วย เพราะมันอธิบายว่าทำไมโพสต์ค้าง
- **แจ้งเตือนเข้า LINE** — ใช้ **LINE Messaging API** ไม่ใช่ LINE Notify
  (Notify ปิดบริการ 31 มี.ค. 2025 · https://notify-bot.line.me/closing-announce)
  - token เข้ารหัส AES-256-GCM แบบเดียวกับ token ของ Meta
  - ส่งจาก worker นอก transaction ของการโพสต์ — ถ้ายิง HTTP ตอนเขียนสถานะ LINE ช้าจะลาก transaction ค้าง
  - เลือกได้ว่าจะให้ส่งเฉพาะเรื่องด่วน / รวมเลยเวลา / ทุกเรื่อง
  - ช่องทางที่ส่งไม่สำเร็จ 10 ครั้งติดถูกปิดเอง ไม่ให้ retry ไปเรื่อยๆ
  - `NOTIFY_TRANSPORT=mock` (ค่าเริ่มต้น) เขียนลงไฟล์แทนการยิงจริง กันส่งข้อความหาคนโดยไม่ตั้งใจ
  - **dead-man switch**: ตั้ง `WORKER_HEARTBEAT_URL` ให้ worker ปิงบริการภายนอกทุกรอบ
    — จำเป็นเพราะ worker ที่ตายแล้วส่งแจ้งเตือนบอกว่าตัวเองตายไม่ได้
- **โปสเตอร์สินค้า** — เทมเพลต 6 แบบ × 3 สัดส่วน ที่ `/poster`
  - ประกอบด้วย sharp: พื้นหลังเทมเพลต + รูปสินค้าจริง + ชั้นข้อความ SVG ฟอนต์ไทย
  - เก็บ "ข้อความที่กรอก" ไว้ด้วย ไม่ใช่แค่ไฟล์ภาพ — เดือนหน้าแก้ราคาแล้วสร้างใหม่ได้ทันที
  - ผลลัพธ์เป็น media_asset ปกติ กด "เอาไปตั้งเวลาโพสต์" ได้เลย
- **หลายรูปต่อโพสต์ (carousel)** — สูงสุด 10 ใบตามเพดานของ Instagram
  - Facebook: อัปทีละใบแบบ `published=false` แล้วผูกเข้าโพสต์เดียวด้วย `attached_media`
  - Instagram: container ลูกใบละรูป (`is_carousel_item=true`) แล้วรวมเป็น container แม่ (`media_type=CAROUSEL`)
  - container ลูกถูกบันทึกทีละใบ ถ้า process ตายตอนสร้างใบที่ 7 รอบหน้าไม่สร้าง 6 ใบแรกซ้ำ
- **ตารางเวลาประจำ** — ตั้งครั้งเดียว โพสต์ใหม่ไหลลงช่องว่างถัดไปเอง ช่องที่จองแล้วถูกข้าม
- **ปฏิทินรายเดือน + ฟีด Instagram ล่วงหน้า**
- **แก้ / เลื่อนเวลา / ทำซ้ำโพสต์** และร่างที่ไม่ถูกส่งจนกว่าจะสั่ง
- **ระบบแจ้งเตือน** — ปิดทีละใบ ย้อนดูได้ที่ `/alerts` เตือนล่วงหน้าเรื่อง worker/token/โควตา
- **ดัชนีฐานข้อมูลจากการวัดจริง** (migration 0002) + โหมดโปรดักชันใน `docker-compose.prod.yml`

## เครื่องมือตรวจของตัวเอง

| คำสั่ง | ตอบคำถามอะไร |
|---|---|
| `npm run smoke` | ตรรกะทำงานถูกไหม — 157 ข้อ ครอบทุกเรื่องที่เคยพังหรืออาจพัง |
| `npm run check-pages` | คนเปิดเว็บแล้วเห็นของที่เขียนไว้ไหม — 13 หน้า + health + การกันคนไม่ล็อกอิน |
| `npm run verify-meta` | ท่าเชื่อมต่อ Meta ที่วางไว้ใช้ได้จริงไหม (ต้องมี token จริง) |
| `npm run setup` | เครื่องใหม่ยังไม่มี `.env` — สร้างให้พร้อมความลับ (ไม่ทับของเดิม) |
| `npm run reset-demo` | ล้างข้อมูลทดสอบให้เหลือแต่ตัวอย่างที่พร้อมโชว์ |

**ลำดับที่ถูกต้องเวลาทดสอบ**: `smoke` → `tsc` → `check-pages` แล้วค่อย `build`
ถ้ารัน `build` ก่อน จะเขียนทับ `.next` ที่ `next dev` กำลังใช้อยู่ (volume เดียวกัน)
เว็บจะขึ้น 500 ทุกหน้าด้วย `Cannot find module './994.js'` — ไม่ใช่บั๊กโค้ด
เจอแล้วให้ `docker compose exec web rm -rf .next && docker compose restart web`

`check-pages` เกิดขึ้นเพราะเคยพลาดจริง: ชุดแฮชแท็กเขียนโค้ดครบ เทสต์ผ่าน build ผ่าน
แต่สคริปต์ที่แทรก JSX หา anchor ไม่เจอแล้วเงียบ — ของเลยไม่เคยขึ้นหน้าเว็บ
บทเรียน: `str.replace` ที่ไม่ match ไม่ error ต้อง assert เสมอ

## รู้ตัวว่ายังไม่ได้ทำ

- **ยังไม่เคยเรียกโมเดลสร้างภาพจริงสักครั้ง** — เส้นทางทั้งหมดทดสอบด้วย local-placeholder
  โครงสร้าง request/response ทำตามเอกสาร OpenRouter (`/api/v1/images` · `data[].b64_json`
  · `input_references`) แต่ยังไม่ผ่านของจริง ครั้งแรกที่ตั้ง key ต้องดูด้วยตาว่าได้ภาพจริง

- **รีเซ็ตรหัสผ่านทางอีเมล** — ยังไม่มี ถ้าลืมรหัสต้องให้เจ้าของตั้งใหม่ให้
  (แต่เปลี่ยนรหัสเองได้แล้วที่หน้าตั้งค่า → บัญชีของฉัน)
- **ราคางาน** — ขอบเขตที่ทำจริงเกินตัวเลข 3,500 + 1,000/เดือน ในสเปกเดิมพอสมควร
  (รายงานข้อ B4/B5) ต้องตีราคาใหม่ก่อนเสนอลูกค้า
